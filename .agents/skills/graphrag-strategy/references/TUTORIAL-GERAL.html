GraphRAG · Tutorial Geral

Rodando o GraphRAG do zero, em qualquer corpus

Este tutorial cobre o processo completo — avaliação do corpus, ajuste de prompts, indexação e consulta — usando o pacote graphrag (testado na versão 3.1.1). Cada fase inclui os bugs reais encontrados ao longo de um projeto de indexação, suas causas exatas e as correções aplicadas, além dos caveats que não são óbvios na documentação oficial. Não é específico de um corpus: os exemplos concretos vêm de um projeto real (material de aulas de HPC/computação paralela), mas o procedimento vale para qualquer coleção de documentos.

Visão geral do pipeline

O processo tem quatro fases, nessa ordem. Pular a Fase 0 é a causa mais comum de reindexações caras e repetidas.

FaseO que fazCusto de LLMReversível?

Fase 0 — Avalie o corpus antes de indexar

Objetivo: saber se o grafo final vai ficar bem distribuído (comunidades de tamanho razoável, sem um "blob" dominante nem fragmentação excessiva) e se o corpus tem lixo/ruído — sem pagar o custo de LLM da indexação completa.

Por que essa fase existe

A indexação completa faz uma chamada de LLM por chunk (extração de entidades) e depois uma por entidade/relação duplicada (resumo de descrições) e uma por comunidade (relatórios). Em um corpus de centenas de arquivos isso são milhares de chamadas e pode levar horas. Descobrir depois desse custo que um arquivo estava "poluindo" o corpus, ou que um subconjunto de documentos ficou isolado do resto do grafo, significa pagar tudo de novo.

Como fazer: --method fast com pipeline customizado

O graphrag tem um modo fast nativo que troca a extração de entidades baseada em LLM (extract_graph) por extract_graph_nlp: extração de sintagmas nominais 100% local (regex, sem rede, sem custo). A clusterização de comunidades (create_communities, algoritmo Leiden) é puramente algorítmica e não sabe nem se importa com qual workflow gerou as entidades — então serve como proxy estrutural válido para saber a forma do grafo.

Crie um root de projeto isolado (não reindexe o projeto real por engano) e configure:

workflows:
  - load_input_documents
  - create_base_text_units
  - create_final_documents
  - extract_graph_nlp
  - prune_graph
  - finalize_graph
  - create_communities
  - create_final_text_units
  # propositalmente SEM create_community_reports_text e generate_text_embeddings
  # (nenhum dos dois é necessário pra avaliar distribuição, e são as fases
  # que custam LLM/embeddings)

extract_graph_nlp:
  text_analyzer:
    extractor_type: regex_english   # default; não depende de nenhum modelo spaCy instalado

Rode com:

graphrag index --root . --method fast --verbose
Detalhe de config fácil de errar

O campo workflows: fica no nível raiz do settings.yaml, e substitui totalmente a lista padrão do --method escolhido — não é um adicional, é uma troca completa. Se você omitir algum workflow de que os outros dependem (ex. remover create_base_text_units mas manter extract_graph_nlp), o pipeline falha por falta de tabela de entrada.

O que avaliar nos resultados

Depois que o índice de preview terminar, ele produz entities.parquet, relationships.parquet e communities.parquet — o suficiente para avaliar distribuição sem nenhum embedding ou relatório de LLM.

import pandas as pd

c = pd.read_parquet("output/communities.parquet")
print("Comunidades por nível:")
print(c["level"].value_counts().sort_index())

print("\nTamanho de comunidade por nível (min/mediana/máx):")
print(c.groupby("level")["size"].describe()[["min", "50%", "max"]])

print("\nMaiores comunidades no nível 0 (candidatas a blob dominante):")
print(c[c["level"] == 0].sort_values("size", ascending=False).head(10)[["id", "size"]])

Sinais a procurar:

  • Uma comunidade de nível 0 muito maior que as outras (ordem de grandeza acima das demais) → corpus com um tópico dominante engolindo o resto.
  • Muitas comunidades de tamanho 1-2 → corpus fragmentado; considere aumentar o tamanho do chunk ou revisar se há material desconexo demais.
  • Uma pasta/fonte inteira isolada numa comunidade sem ligação com o resto → sinal de que esse material pertence a outro domínio e talvez devesse ser um índice separado.
Bug: documents.parquet não guarda o caminho, só o nome do arquivo

A coluna title em documents.parquet é só o basename (ex.: "AGENTS.md"), não o caminho relativo. Se você tentar agrupar por pasta de origem fazendo title.str.split("/").str[0], o resultado não vai fazer sentido — todo arquivo com o mesmo nome em pastas diferentes colapsa junto. Para saber a distribuição real por pasta, refaça a varredura direto no filesystem com o mesmo regex do file_pattern, em vez de depender do parquet: 

import re, pathlib
from collections import Counter

pat = re.compile(r'<mesmo regex do file_pattern do settings.yaml>')
base = pathlib.Path("/caminho/do/corpus")
hits = [(f.stat().st_size, str(f.relative_to(base)))
        for f in base.rglob("*") if f.is_file() and pat.match(str(f.relative_to(base)))]

print(Counter(r.split('/')[0] if '/' in r else '(raiz)' for _, r in hits).most_common(20))
Caveat: qualidade semântica menor

O extrator regex_english é orientado a inglês. Em corpus em outro idioma, ele ainda encontra "sintagmas nominais" (sequências de palavras capitalizadas/repetidas), mas com nomenclatura de entidade mais crua/ruidosa que a extração via LLM tunada. Isso não invalida o preview porque o objetivo aqui é a forma da distribuição (tamanho e conectividade de comunidades), não a qualidade de nomenclatura — mas não use esse índice de preview para avaliar qualidade de extração, só estrutura.

Achado real de projeto: arquivos de meta-navegação

Rodando esse preview num corpus real de ~280 arquivos, descobrimos que 21,7% dos arquivos eram AGENTS.md — documentos de navegação de repositório ("esta pasta contém X, Y, Z"), não conteúdo real. Nenhum file_pattern típico (que só exclui por nome de diretório, como node_modules/ ou dotfiles) filtra isso por nome de arquivo. Vale adicionar uma exclusão explícita por nome (AGENTS.md, README.md e afins) se eles não forem conteúdo relevante no seu caso.

Fase 1 — Setup inicial

Objetivo: ter um settings.yaml válido e a pasta prompts/ com os arquivos que o pipeline espera.

graphrag init

pip install graphrag
mkdir -p meu-projeto/input
graphrag init --root ./meu-projeto
Bug: graphrag init é interativo e quebra sem TTY

Em ambientes não-interativos (scripts, CI, agentes automatizados), graphrag init pergunta "Specify the default chat model to use [gpt-4.1]:" e aborta com EOFError/"Aborted." se não houver terminal interativo pra responder. Nesse caso, monte a estrutura manualmente: crie settings.yaml, prompts/, cache/, output/, logs/ à mão (veja o exemplo completo mais abaixo).

Sempre junto: .env e .gitignore

A chave de API (${SUA_API_KEY} no settings.yaml) normalmente vem de um arquivo .env no root do projeto, que o graphrag carrega automaticamente. Sempre que copiar um .env para um novo root (por exemplo, ao criar o root de preview da Fase 0), copie também o .gitignore da mesma pasta de origem, se existir — .env guarda segredo e deveria estar sempre pareado com a exclusão do controle de versão.

Bug: diretório prompts/ ausente ou incompleto

Sintoma: Pipeline error: [Errno 2] No such file or directory: 'prompts/extract_graph.txt' na fase extract_graph. Causa: o settings.yaml referencia arquivos de prompt (extract_graph.txt, summarize_descriptions.txt, etc.) que precisam existir em disco — eles não são gerados automaticamente pelo pipeline de indexação, só pelo graphrag init (que pode não ter rodado, ou ter sido interrompido) ou pelo graphrag prompt-tune (Fase 2). Se estiverem faltando, gere os padrões de fábrica via Python: 

python3 -c "
from graphrag.prompts.index.extract_graph import GRAPH_EXTRACTION_PROMPT
from graphrag.prompts.index.community_report import COMMUNITY_REPORT_PROMPT
from graphrag.prompts.index.community_report_text_units import COMMUNITY_REPORT_TEXT_PROMPT
from graphrag.prompts.index.summarize_descriptions import SUMMARIZE_PROMPT
from pathlib import Path

Path('prompts').mkdir(exist_ok=True)
Path('prompts/extract_graph.txt').write_text(GRAPH_EXTRACTION_PROMPT)
Path('prompts/community_report_graph.txt').write_text(COMMUNITY_REPORT_PROMPT)
Path('prompts/community_report_text.txt').write_text(COMMUNITY_REPORT_TEXT_PROMPT)
Path('prompts/summarize_descriptions.txt').write_text(SUMMARIZE_PROMPT)
"
Bug: nomes de arquivo de prompt não batem com o que o config espera

O bloco community_reports: do settings.yaml tem dois campos, graph_prompt e text_prompt, apontando para dois arquivos diferentes (community_report_graph.txt e community_report_text.txt). É fácil só criar um dos dois (ou criar com nome errado, como community_reports.txt no singular) e a falha só aparece depois, na fase create_community_reports, com outro FileNotFoundError — geralmente depois de já ter pago o custo de extract_graph. Confirme os dois arquivos existem antes de rodar o índice completo.

Fase 2 — Ajustar prompts ao domínio (prompt-tune)

Objetivo: os prompts padrão de extração são genéricos (tipos de entidade como organization, person, geo, event, em inglês). O prompt-tune gera prompts específicos do seu domínio e idioma, usando exemplos do próprio corpus.

O achado mais importante desta fase: você pode testar sem indexar nada

graphrag prompt-tune lê os documentos de entrada diretamente via input_storage/input do settings.yaml — o mesmo mecanismo do index, mas fazendo o próprio chunking e amostragem, sem depender de nenhum output/*.parquet ou cache/ pré-existente. Ou seja: dá pra rodar como o primeiro comando em um root totalmente vazio.

Caveat: isso só vale para os prompts de indexação

Uma vez que você decide aplicar o prompt tunado e rodar o índice completo de verdade, qualquer mudança de texto no prompt invalida o cache daquela fase por inteiro — o conteúdo do prompt entra no hash da chave de cache. Não tem meio-termo: teste antes num corpus pequeno (recomendado abaixo), ou pague o reprocessamento completo depois de mudar o prompt no índice grande.

Fluxo recomendado: mini-corpus isolado

  1. Copie um subconjunto pequeno e coerente do corpus real (algumas centenas de KB a poucos MB) para um root de teste separado, excluindo meta-arquivos de navegação (tipo AGENTS.md).
  2. Monte um settings.yaml mínimo apontando pra essa pasta.
  3. Rode: 
    graphrag prompt-tune \
  --root . \
  --language <idioma> \
  --domain "<descrição do domínio + o que você quer FAZER com o conteúdo depois>" \
  --chunk-size 2400 \
  --selection-method auto \
  --limit 20 \
  --min-examples-required 3 \
  --discover-entity-types \
  --verbose
  4. Inspecione os prompts gerados em prompts/ antes de aplicar ao índice grande.

Notas sobre as flags:

  • --domain deve descrever não só o assunto, mas o que você quer fazer com o conteúdo depois — isso molda a persona embutida no prompt de community_reports, que é o que mais influencia a qualidade das respostas de síntese depois.
  • --discover-entity-types deixa o modelo descobrir tipos de entidade específicos do corpus em vez de reusar uma lista genérica fixa — normalmente produz extração mais relevante.
  • --selection-method auto usa embeddings pra escolher chunks representativos do corpus inteiro (em vez de random ou os primeiros top).
Bug: prompt-tune nunca gera community_report_text.txt

Ele só produz três arquivos: extract_graph.txt, summarize_descriptions.txt e community_report_graph.txt — nunca o text_prompt (community_report_text.txt). Como o settings.yaml referencia os dois, sem essa correção o índice completo quebra na fase create_community_reports com FileNotFoundError. Gere o padrão de fábrica pra esse arquivo específico (comando na Fase 1) antes de rodar o índice completo.

Boa prática: escolha do corpus de teste

Exclua arquivos de meta-documentação (AGENTS.md, README.md de navegação) do mini-corpus de teste — eles não são conteúdo real e distorcem os exemplos que o prompt-tune usa pra calibrar o prompt.

Fase 3 — Indexação completa

A fase mais cara e mais frágil. A maior parte dos bugs reais deste tutorial apareceu aqui.

graphrag index --root . --verbose

BUG CRÍTICO: race condition no cache de arquivos

Sintoma: o índice falha de forma não-determinística durante extract_graph ou summarize_descriptions, alternando entre execuções diferentes com: 

FileNotFoundError: [Errno 2] No such file or directory: '.../cache/summarize_descriptions/<hash>_v4'
TypeError: the JSON object must be str, bytes or bytearray, not NoneType

Apagar o cache/ e reindexar "resolve" temporariamente, mas o erro volta em execuções seguintes — sinal de bug de concorrência, não de config quebrada.

Causa raiz (rastreada no código-fonte do pacote):

  1. concurrent_requests é um campo global, não por modelo — o campo real fica em GraphRagConfig.concurrent_requests, no nível raiz do settings.yaml, com default 25. Colocar concurrent_requests dentro de um bloco de completion_models/embedding_models é silenciosamente ignorado — esse campo não existe no schema de model config.
  2. O cache de arquivos (FileStorage) não é atômico: set() abre o arquivo direto em modo escrita (trunca antes de escrever), sem arquivo temporário + rename.
  3. JsonCache.get() faz check-then-use (TOCTOU): checa se o arquivo existe, e só depois, numa chamada separada, lê o conteúdo.
  4. Com concorrência alta (25 por default), é comum duas chamadas processarem a mesma chave de cache ao mesmo tempo — acontece sempre que a mesma entidade é descrita em vários chunks do corpus (muito comum em corpus real). Uma trunca o arquivo enquanto a outra lê → JSON incompleto → é deletado → uma terceira chamada que já tinha confirmado que o arquivo existia encontra FileNotFoundError ao tentar abri-lo.

Correção: no nível raiz do settings.yaml:

concurrent_requests: 3   # ou 1, garantidamente seguro (sequencial), porém mais lento

concurrent_requests: 1 elimina a race por construção (zero concorrência possível). 3 reduz drasticamente a chance de colisão e foi validado em produção (reindexação completa, milhares de chamadas, zero erros do início ao fim) — mais rápido que 1, mas não garantidamente livre de colisão. Se a race reaparecer, caia para 1.

Caveat: reindexação não é incremental após mudar prompt

O conteúdo do prompt entra no hash da chave de cache. Trocar qualquer texto em extract_graph.txt/summarize_descriptions.txt/ community_report_*.txt invalida o cache inteiro daquela fase — todos os chunks/entidades precisam ser reprocessados, não só os que mudaram. Já mudar apenas configs que não afetam o texto do prompt final enviado ao modelo (ex.: parâmetros de cluster_graph, que roda depois da extração) não invalida o cache de extração.

Boa prática: sempre salve um backup do estado que funciona

Antes de mexer em qualquer coisa depois de um índice bem-sucedido:

tar czf output_$(date +%F)_ok.tar.gz output/
cp settings.yaml settings.yaml.ok

Sinais de que o índice terminou bem

python3 -c "
import pandas as pd, glob, os
for f in sorted(glob.glob('output/*.parquet')):
    print(f'{len(pd.read_parquet(f)):7}  {os.path.basename(f)}')
"

Devem existir e ter linhas > 0: documents, text_units, entities, relationships, communities, community_reports. Se usou embeddings, confira também as 3 tabelas do LanceDB (entity_description, text_unit_text, community_full_content) — todas com a mesma dimensão do embedding configurado.

Bug histórico (versões antigas): as 3 famílias de embedding se sobrescreviam

Em algumas versões/configs, as três famílias de embedding (entity_description, text_unit_text, community_full_content) eram gravadas na mesma tabela do vector store em modo overwrite — a última a rodar apagava as anteriores, deixando só uma família de vetores no banco (o sinal é o número de linhas da tabela bater exatamente com o tamanho de uma das três, e as outras não aparecerem em nenhum lugar). Isso quebra local/drift/basic search (que dependem de embedding), enquanto global continua funcionando normalmente (não usa vetores). Se isso acontecer, confirme no seu vector store se existem tabelas/namespaces separados por família antes de reindexar.

Fase 4 — Consultando o índice

Quatro métodos, comportamentos e custos bem diferentes.

MétodoComo funcionaChamadas de LLM por perguntaQuando usar
localBusca vetorial + contexto local (entidades/relações próximas)1Perguntas específicas sobre um tópico/entidade
globalMap-reduce sobre todos os relatórios de comunidade de um nível1 por relatório do nível (pode ser centenas)Visão macro ("quais os temas principais?") — sempre com --community-level 0
basicBusca vetorial simples sobre os chunks de texto, sem grafo1Perguntas pontuais, quando não precisa de síntese via grafo
driftParte de uma entidade e navega o grafo com múltiplos follow-ups internosVárias (primer + follow-ups, acumula)Perguntas que precisam de navegação/aprofundamento, uso didático
Bug: drift falha com modelo local pequeno

Sintoma: drift_search quebra com JSONDecodeError: Expecting value: line 1 column 1 (char 0) vindo de dentro da validação de schema JSON do litellm. Causa: a etapa de "primer" do drift exige que o modelo retorne JSON estruturado válido (response_format: json_object); um modelo local pequeno (poucos bilhões de parâmetros) pode retornar uma resposta vazia ou mal-formada, e a validação de schema não degrada graciosamente — ela lança excessão e derruba a consulta inteira. Correção: configure drift_search.completion_model_id para um modelo mais confiável (tipicamente o mesmo usado em produção/API paga), não o modelo local leve.

Caveat: query não tem cache

Diferente da indexação, graphrag query não cacheia nada — cada pergunta repetida custa de novo, mesmo que seja exatamente a mesma pergunta de antes.

Caveat: global no nível default pode ser caro

O nível de comunidade default para global_search geralmente é um nível intermediário (granular), que pode ter centenas de relatórios — logo, centenas de chamadas de LLM por pergunta. Sempre especifique --community-level 0 (o nível mais macro, menos relatórios) a menos que precise de granularidade fina. 

graphrag query --root . --method global --community-level 0 "sua pergunta"
Boa prática: sequência de iterações com drift

A CLI de query não mantém estado entre chamadas — cada invocação é independente, sem histórico. Pra simular uma "conversa" de aprofundamento progressivo: rode uma pergunta, leia a resposta, escolha um conceito que apareceu mas não foi perguntado diretamente, e faça a próxima pergunta citando esse conceito pelo nome exato usado na resposta anterior — isso ajuda a busca a encontrar o mesmo nó do grafo. Repita até esgotar profundidade nova, ou até o sistema admitir que não tem a informação — ambos os desfechos são úteis: o segundo mostra os limites reais do corpus indexado, em vez de alucinar uma conexão que não existe.

Referência rápida de comandos

# Fase 0 — preview estrutural (zero LLM)
graphrag index --root <root-preview> --method fast --verbose

# Fase 1 — validar config sem rodar nada
graphrag index --root . --dry-run

# Fase 2 — ajustar prompts (funciona sem índice prévio)
graphrag prompt-tune --root . --language <idioma> \
  --domain "<descrição + objetivo>" --selection-method auto \
  --discover-entity-types --verbose

# Fase 3 — índice completo
graphrag index --root . --verbose

# Fase 4 — consultas
graphrag query --root . --method local  "pergunta específica"
graphrag query --root . --method global --community-level 0 "pergunta ampla"
graphrag query --root . --method basic  "pergunta pontual"
graphrag query --root . --method drift  "pergunta que precisa navegar o grafo"

# Backup do estado que funciona
tar czf output_$(date +%F)_ok.tar.gz output/
cp settings.yaml settings.yaml.ok
